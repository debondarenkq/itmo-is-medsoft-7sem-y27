# Лабораторная 2: безопасность

## Запуск

Практический сценарий самостоятельного запуска и защиты — [defense.md](defense.md).

Один раз создайте учебный CA, сертификат сервера, ключ подписи JWT и ключ межсервисных запросов:

```sh
make certs
```

Команда сохраняет полный существующий набор ключей и создаёт его только при отсутствии файлов. Неполный набор не заменяется автоматически. Непосредственный генератор `scripts/generate-security.sh` также отказывается заменять существующие ключи. Файлы находятся в игнорируемом `deploy/security/`; закрытые ключи, пароли, TOTP-секреты и токены в репозиторий не включаются.

Файлы разделены по назначению:

```text
deploy/security/
  tls/
    ca/          корневой CA: ca.crt, ca.key, ca.cnf, ca.srl
    server/      сертификат Nginx: server.crt, server.key, server.cnf, server.csr
  jwt/           signing.key — подпись access-токенов
  services/      service.key — внутренние запросы между сервисами
```

В macOS откройте **Связка ключей**, импортируйте `deploy/security/tls/ca/ca.crt` и установите доверие для SSL к этому учебному CA. Это ручной шаг первоначальной настройки. Проверка сертификатов в приложении остаётся системной: без доверия к CA соединение будет отклонено.

```sh
make prepare  # один раз, с интернетом
make demo     # каждый запуск без сборки и скачиваний
```

Адрес клиента — `https://localhost:8443`. В настройках допустим только HTTPS. Если ранее был сохранён адрес из лабораторной 1, измените его в HIS → Настройки. Nginx принимает внешние запросы только через TLS 1.3; HTTP-порт используется внутри сети Compose и наружу не публикуется. Сами Go-сервисы наружу также не публикуются. PostgreSQL на `localhost:55432` оставлен для учебной диагностики, как в лабораторной 1; для работы приложения он не нужен.

У корневого CA **Subject = Issuer**: `O=ITMO`, `OU=MedSoft 2026/27 367907`, `CN=HIS Teaching Root CA`. У серверного сертификата **Subject** содержит `CN=localhost`, а **Issuer** — имя подписавшего его CA. В SAN перечислены `localhost`, `127.0.0.1`, `::1`. Серверный сертификат не является корневым CA и имеет назначение `serverAuth`.

## Просмотр сертификатов в нативном клиенте

Откройте **HIS → Сертификаты сервера…** либо одноимённую кнопку в настройках. Отдельное окно показывает сертификат сервера и доступную цепочку `serverTrust`: Subject (включая O, OU, CN), Issuer, начало и окончание срока действия, отпечаток SHA-256 и полный публичный сертификат в PEM. Текст можно выделить и скопировать. Для каждого сервера указаны адрес и время получения; цепочка доверия может включать корневой сертификат из системного хранилища, а не только переданные сервером сертификаты.

Сведения перехватываются из настоящего TLS challenge сетевого клиента, включая вход, обновление токенов и импорт. Кнопка «Проверить подключение» выполняет запрос `/live` через новую сессию, чтобы повторить TLS handshake без входа в аккаунт. Сертификат сохраняется для просмотра и при последующем отказе системной проверки доверия; наличие сертификата в окне не означает доверия к нему. Ошибка подключения выводится в этом же окне. Проверка остаётся штатной: делегат возвращает `.performDefaultHandling`, исключений доверия и отключения проверки нет.

## Первый вход и аккаунты

Откройте отдельное приложение `HISAdmin.app`. Вход медработников находится в `HIS.app`; переключателя ролей в приложениях нет. Первичная настройка разделена на три этапа: пароль, двухфакторная защита, завершение. Пароль — минимум 8 символов, большие и маленькие буквы и цифра, не более 72 байт. Поля позволяют показать пароль, индикаторы отмечают выполненные требования. На втором этапе доступны QR-код TOTP, строка секрета и кнопка копирования. Добавьте её в приложение-аутентификатор: SHA-1, 6 цифр, период 30 секунд. Настройка сохраняется только после проверки кода. Администратор один, имя входа `admin`; последующие входы требуют пароль и TOTP. Восстановления TOTP нет. Уже принятый временной шаг TOTP повторно не принимается; допускается отклонение часов на один шаг.

Администратор создаёт медработника, выбирает роль (по умолчанию `other`) и нажимает «Создать аккаунт» в списке медработников. Логин уникальный, 3–16 символов. Пароль генерируется сервером: ровно 12 символов из `A–Z`, `a–z`, `0–9`. Пароль показывается один раз в окне создания или сброса. Хранятся только bcrypt-хэши с cost 12. В разделе «Аккаунты» доступны поиск по логину и медработнику, фильтр активности, создание, редактирование логина и роли, активация/деактивация и генерация нового пароля. В списке отображаются имя медработника и роль. Хэши паролей API не возвращает.

Один аккаунт связан максимум с одним медработником, один медработник — максимум с одним аккаунтом. База допускает самостоятельный неадминистративный аккаунт, но публичный API создаёт аккаунт только для существующего неудалённого медработника. После логического удаления сотрудника identity показывает связанный аккаунт неактивным и отклоняет его вход, refresh и защищённые запросы по актуальному состоянию staff. Запись активности аккаунта в identity хранится отдельно; события и фоновая синхронизация не используются.

Медработник входит по выданным логину и паролю. Профиль и автор ЭМК определяются аккаунтом; ручного выбора действующего лица нет. Переданный в запросе `staff_id` должен совпадать с медработником из проверенного access-токена.

| Действие | Администратор | doctor | nurse | laboratory-technician / other |
|---|---|---|---|---|
| Медработники, справочник диагнозов, аккаунты, аудит | Да | Нет | Нет | Нет |
| Просмотр пациентов, ЭМК и истории | Нет | Да | Да | Да |
| Создание/изменение/удаление пациентов, создание ЭМК | Нет | Да | Да | Нет |
| Разблокировка и сохранение изменений ЭМК | Нет | Да | Нет | Нет |

Чтение отдельной записи медработника и диагнозов разрешено медработникам для отображения и межсервисной проверки справочников. Управление справочниками остаётся административной операцией. Права проверяются сервером для каждого запроса, включая обращения непосредственно к Go-сервисам.

## Сессии

Access-токен — JWT с подписью Ed25519 (`alg=EdDSA`), `iss=his-identity`, `aud=his-api`, UUID аккаунта в `sub`, ролью, UUID медработника, `iat`, `exp`, `jti`. Срок жизни — 5 минут. Refresh-токен — криптографически случайная строка; в БД сохраняется SHA-256, срок жизни — 24 часа. При refresh оба токена заменяются, старый refresh погашается в транзакции. Из двух конкурентных обновлений одного refresh только одно успешно.

Деактивация и сброс пароля отзывают refresh-токены и меняют версию сессий аккаунта в одной транзакции identity. Access JWT содержит эту версию; при каждой авторизации identity сверяет её с аккаунтом. Поэтому старый JWT после блокировки или сброса пароля также отклоняется. Количество удалённых refresh-токенов записывается в аудит.

Staff единолично хранит ФИО, должность, роль и состояние удаления сотрудника. Identity не хранит таблицу профилей сотрудников. При входе, refresh и каждой авторизации сотрудника identity делает прямой запрос к внутреннему API staff. В refresh-сессии и JWT сохраняется номер изменения роли; staff увеличивает его при фактической смене роли. Несовпадение версии или удаление сотрудника отклоняет запрос (401), даже если роль успели изменить обратно. Изменение ФИО не завершает сессии. При недоступном staff операция отклоняется с 503; вход и авторизация администратора от staff не зависят. Проверка сотрудника и дальнейшее доменное изменение находятся в разных транзакциях; распределённой атомарности нет.

Списки аккаунтов, поиск по ФИО и имена акторов аудита собираются из данных identity и прямых ответов staff. Фоновых обработчиков, очередей, outbox и репликации профилей нет. Поля публичного API и оба приложения сохраняются: роль можно менять как из карточки сотрудника, так и из редактора аккаунта.

Редактор аккаунта вызывает внутренний API staff для изменения роли, а локальные поля аккаунта сохраняет в identity. Identity заранее проверяет конфликт логина; HTTP-запрос выполняется вне SQL-транзакции. Это две последовательные операции: при сетевой ошибке или конкурентном конфликте после сохранения роли остальные поля аккаунта могут не сохраниться. Повторное чтение показывает фактическое состояние, повторное сохранение безопасно. Межсервисный аудит фиксирует намерение до выполнения запроса и его результат; отдельная запись аудита staff при смене роли из аккаунта не создаётся, операция отражается как изменение аккаунта.

Access действует не более 5 минут и дополнительно проверяется по текущему состоянию аккаунта и сотрудника при каждом запросе. После блокировки, сброса пароля, смены роли или удаления сотрудника старые токены отклоняются до истечения `exp`. Новый вход получает актуальные права, а обновление недействительного refresh отклоняется. Выход отзывает текущий refresh и удаляет локальное состояние клиента. В macOS токены хранятся только в памяти. Одновременные запросы клиента используют одну задачу обновления, чтобы не конкурировать за refresh. После неуспешного refresh требуется новый вход. Автоматического повторения записывающих запросов нет.

## Сервисы и аудит

Аккаунты, TOTP, refresh-токены и аудит принадлежат отдельному identity-сервису и его БД. Медработниками владеет staff; identity не читает его таблицы. Публичный контракт безопасности — `contracts/security.yaml`; документация работающего сервера — `/docs/security/openapi.json`. Identity проверяет подпись JWT, текущее состояние аккаунта и сотрудника; staff, clinical и catalog обращаются к внутреннему `/internal/authorize` identity. Внутренние запросы требуют отдельный ключ `SERVICE_KEY_FILE`. Эти маршруты не опубликованы в Nginx. При недоступной авторизации операция отклоняется с 503. Клинические проверки справочников передают исходный Bearer-токен через gateway.

Аудит содержит UUID события, серверное время, инициатора и сообщение. Инициаторы:

- `account:<UUID>` — аутентифицированный аккаунт;
- `anonymous:<адрес>:request:<UUID>` — отдельный неаутентифицированный запрос, включая неуспешный вход;

Записываются настройка/вход администратора, вход медработника, неуспешные входы, отказы доступа, запросы и результаты изменений сотрудников/пациентов/ЭМК/аккаунтов, ротация и отзыв токенов. Для доменных HTTP-изменений до выполнения сохраняется намерение, после выполнения — HTTP-результат. Тип события задаётся общим enum `AuditEventKind` из `contracts/audit.yaml`. Типы HTTP-запроса и событий генерируются через `oapi-codegen` отдельно в каждом потребителе. Сервис находит операцию стандартным OpenAPI-router и читает `x-audit` из сгенерированной спецификации; ручного разбора маршрутов через строковый switch нет. Межсервисный аудит передаёт тип события, название операции и отдельные поля `method`, `path`, `status`; identity формирует описание результата из типизированного запроса. Если предварительная запись аудита недоступна, изменение не выполняется. Если хранилище аудита отказывает уже после доменного изменения, предварительная запись остаётся, ошибка записи результата попадает в журнал сервиса. Между разными БД распределённой транзакции нет. Изменения аккаунта и локальный отзыв refresh-токенов фиксируются атомарно с собственной записью аудита.

В интерфейсе события содержат время, тип с цветным значком, имя автора и описание. Тип события хранится отдельно; фильтрация по типу и периоду выполняется сервером до пагинации. События расположены по времени от старых к новым; режим «Последние события» обновляет последние 50 записей каждую секунду. Для просмотра более ранних записей отключите этот режим и используйте страницы. Пароли, TOTP-секреты и токены в сообщения аудита не включаются. API для изменения или удаления аудита нет. WebSocket не используется.

Вход и настройка ограничены 20 попытками в минуту на адрес подключения. Все ответы API защищены от кэширования заголовком `Cache-Control: no-store`.

## Проверки

```sh
make check test
make integration
make macos-build
```

Сквозная проверка с существующим администратором запрашивает пароль и TOTP интерактивно:

```sh
python3 scripts/smoke.py
```

Для полностью автоматической проверки первоначальной настройки используйте **отдельный проект с новой базой**, остановив основной проект, если он занимает те же порты:

```sh
./scripts/compose.sh -p his-lab2-check up --build -d --wait
python3 scripts/smoke.py --bootstrap
./scripts/compose.sh -p his-lab2-check down
```

`--bootstrap` создаёт случайный пароль и TOTP только в памяти тестового процесса; такой проект предназначен для тестов, а не для ручного входа. Сквозная проверка требует доверия к переданному через `--ca` CA, проверяет имя сервера и использует TLS 1.3. Никаких `insecure`/отключений проверки сертификата нет. Проверяются все роли, привязка автора, повторное использование refresh, четыре причины отзыва, аудит, CRUD пациентов, атомарность ЭМК, история и восстановление. Unit-тесты TOTP используют векторы RFC 6238; интеграционные тесты проверяют конкурентную ротацию и транзакционные отзывы.

## Медицинские экраны

У медработника есть разделы «Пациенты» и «ЭМК». Списки поддерживают серверный поиск по ФИО и номеру карты; «ЭМК» показывает только пациентов с картой. Постоянный номер формата `ЭМК-000001` назначает PostgreSQL; UUID остаётся внутренним идентификатором API. Миграция добавляет номера существующим картам без удаления данных.

Карта открывается в основной области с сохранением бокового меню. Заголовок содержит ФИО, дату рождения, возраст, пол и номер ЭМК. Справа показаны роль и доступные права; диагнозы, назначения и история остаются отдельными вкладками. Врач разблокирует карту, редактирует черновик и сохраняет его целиком. Во время редактирования переход по боковому меню блокируется; закрытие и выход требуют подтверждения. Редактор назначения показывает обязательное содержание и счётчик символов (3–128 — действующее ограничение назначения).

Макеты адаптированы к сущностям лабораторных 1–2: самостоятельные текстовые записи, анализы, файлы и удаление аккаунтов не входят в эту доработку. Администратор управляет справочниками, аккаунтами и аудитом; медицинские экраны остаются рабочим местом медработника.

## Сброс к демонстрационным данным

```sh
make reset       # или make reset-demo
```

Это явная разрушающая команда для локальной демонстрации: данные аккаунтов (включая существующего администратора), TOTP, сеансов, аудита, сотрудников, диагнозов, пациентов и ЭМК заменяются учебным набором. Контейнеры и тома HIS и LIS пересоздаются; PostgreSQL создаёт базы при первом запуске, сервисы применяют миграции с нуля. Резервные копии при учебном сбросе не создаются. TLS-сертификаты и ключи сохраняются. Прежние сессии перестают действовать после удаления аккаунтов и токенов из БД.

Набор содержит 4 активных сотрудника с ролями doctor, nurse, laboratory-technician и other, одного удалённого сотрудника, 5 активных и один удалённый диагноз, 6 пациентов, 3 ЭМК (включая пустую) и 9 событий их истории, а также 7 назначений лабораторных анализов. В картах есть диагнозы, изменение назначения и отменённое назначение; трое пациентов ещё не имеют ЭМК. Все имена и данные — синтетические.

**После reset аккаунтов нет.** Откройте HISAdmin и выполните обычную первоначальную настройку пароля и TOTP администратора. Для создания демо-аккаунтов запустите отдельный скрипт:

```sh
make demo-accounts
# или python3 scripts/create-demo-accounts.py --url https://localhost:8443
```

Скрипт запрашивает пароль и текущий TOTP администратора, входит через `/api/v1/auth/login`, получает сотрудников через `/api/v1/staff` и создаёт аккаунты через `/api/v1/accounts`. При отсутствии нужного сотрудника он создаёт его обычным POST-запросом. Прямого доступа к БД, Go-модулям сервисов и межсервисным ключам у скрипта нет. Создание аккаунтов и действия скрипта проходят обычные серверные проверки и аудит. Соединение использует HTTPS, проверку CA и имени сервера, TLS 1.3; после работы скрипт завершает свой сеанс.

Четыре обычных аккаунта — `demo_doctor`, `demo_nurse`, `demo_lab`, `demo_other`. Исходные профили лежат в `examples/demo-staff.json`. Сервер генерирует пароль из 12 латинских букв и цифр и хранит bcrypt-хэш. Скрипт сразу после создания каждого аккаунта сохраняет выданный пароль в **игнорируемый Git** файл `build/demo-accounts.json` с правами 0600. Пароли и токены не печатаются. Повторный запуск пропускает существующие аккаунты и не меняет их пароли; если выданный пароль не был сохранён или затем изменён, его можно сбросить в HISAdmin.

`make reset` использует существующие образы, не скачивает зависимости и не пересобирает образы. После обновления кода сначала выполните `make prepare-local`. На время пересоздания схем API остановлены. Затем сервисы создают актуальные таблицы, и базы заполняются учебными данными. Старый файл демо-паролей удаляется. Если заполнение не завершилось, gateway остаётся остановленным. В открытых клиентах после reset требуется новый вход.

### Пустая учебная установка

Миграции identity и staff сразу создают актуальную схему. Код переноса аккаунтов, поддержка прежних схем и копирование старых пользователей отсутствуют. Для пустой установки HIS и LIS выполните `make fresh`; администратора, сотрудников и аккаунты создайте через приложения. Обычный запуск сохраняет данные текущей установки.

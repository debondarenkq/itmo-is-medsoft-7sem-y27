# HTTP API HIS

Базовый адрес при запуске Compose: `http://localhost:8080`. Все бизнес-методы имеют префикс `/api/v1`. Для JSON-тела обязателен `Content-Type: application/json`. PUT полностью заменяет редактируемые поля, служебные поля назначает сервер. Неизвестные поля тела отклоняются. Ограничения длины считаются в символах Unicode.

Создание возвращает 201 и объект, чтение/изменение — 200, удаление — 204 без тела. Ошибки: 400 — неверные поля или команды; 404 — объект отсутствует; 409 — уникальность, конфликт версии, запрещённая бизнес-операция; 415 — неверный Content-Type; 503 — справочный сервис недоступен; 500 — внутренняя ошибка.

```json
{"error":{"code":"PATIENT_HAS_RECORD","message":"Нельзя удалить пациента, для которого создана ЭМК"}}
```

Списки: `?q=Иван&limit=50&offset=0`, limit 1–200. Ответ: `{"items":[],"total":0,"limit":50,"offset":0}`. Для медработников и диагнозов `include_deleted=true` включает архивные записи. GET отдельного объекта позволяет посмотреть мягко удалённую запись; редактировать её нельзя.

## Медработники

| Метод | Путь | Действие |
|---|---|---|
| GET / POST | `/api/v1/staff` | Список / создание |
| GET / PUT / DELETE | `/api/v1/staff/{id}` | Просмотр / изменение / мягкое удаление |

Тело создания/изменения:

```json
{"first_name":"Анна","last_name":"Петрова","position":"Терапевт"}
```

Все три поля обязательны: 3–24 символа после удаления пробелов по краям. Удаление устанавливает `deleted_at`. Удалённый сотрудник сохраняется в БД и истории, но не может подписывать новые изменения ЭМК.

## Диагнозы

| Метод | Путь | Действие |
|---|---|---|
| GET / POST | `/api/v1/diagnoses` | Список / создание |
| GET / PUT / DELETE | `/api/v1/diagnoses/{id}` | Просмотр / изменение / мягкое удаление |
| POST | `/api/v1/diagnoses/import` | Импортировать диагнозы из выбранного JSON-файла |

Тело создания/изменения:

```json
{"code":"J00.00","name":"Острый назофарингит"}
```

Код — 6 символов, наименование — 3–24; оба уникальны, включая архивные записи. При создании базы справочник пуст. Импорт получает список из выбранного пользователем файла, делает upsert по коду, обновляет названия и восстанавливает активность импортируемых записей. Другие диагнозы остаются без изменений. Повторная загрузка сохраняет ID. Конфликт имени с другой записью откатывает весь импорт. Удаление архивирует диагноз; добавить его в ЭМК больше нельзя, ранее добавленные снимки сохраняются.


### Файл импорта

Кнопка «Загрузить из файла» открывает выбор JSON-файла. Flutter-клиент отправляет его содержимое как тело `POST /api/v1/diagnoses/import` с `Content-Type: application/json`. Серверу не передаётся путь к локальному файлу; multipart не требуется.

```json
{
  "diagnoses": [
    {"code":"J00.00","name":"Острый назофарингит"},
    {"code":"I10.00","name":"Гипертензия"}
  ]
}
```

Файл содержит от 1 до 1000 записей, ограничение тела — 1 MiB. Неизвестные поля, неверный JSON, некорректные записи, повторяющиеся коды или наименования в файле отклоняются до сохранения. Ошибки полей указывают индекс, например `diagnoses[1].code`. Ответ — `{"items":[...]}` со всеми импортированными записями. Ни одна запись не сохраняется при ошибке любого элемента.

Файл `examples/diagnoses.json` содержит пять учебных примеров для ручного выбора. Автоматическая загрузка при запуске отсутствует.

## Пациенты

| Метод | Путь | Действие |
|---|---|---|
| GET / POST | `/api/v1/patients` | Список / создание |
| GET / PUT / DELETE | `/api/v1/patients/{id}` | Просмотр / изменение / физическое удаление |

```json
{
  "first_name":"Иван",
  "last_name":"Иванов",
  "middle_name":null,
  "birth_date":"2000-01-01",
  "administrative_sex":"UNKNOWN",
  "comment":"Учебный пациент"
}
```

Имя/фамилия — 1–64 символа; отчество — необязательное, 1–64 символа при наличии (пустое нормализуется в null). Дата — YYYY-MM-DD, обязательна, не в будущем. Пол: `M`, `F`, `UNKNOWN`, отображается как М/Ж/НУ. Комментарий необязателен, до 32 символов. Ответ также содержит `has_record`.

DELETE физически удаляет пациента только без ЭМК. Внешний ключ обеспечивает запрет на уровне PostgreSQL, включая конкурентные запросы; API возвращает 409 `PATIENT_HAS_RECORD`.

## ЭМК

| Метод | Путь | Действие |
|---|---|---|
| POST | `/api/v1/patients/{id}/record` | Создать единственную карту пациента |
| GET | `/api/v1/patients/{id}/record` | Получить карту пациента |
| GET | `/api/v1/records/{id}` | Получить текущее состояние карты |
| POST | `/api/v1/records/{id}/changes` | Атомарно сохранить набор команд |
| GET | `/api/v1/records/{id}/history` | История по sequence, с limit/offset |
| GET | `/api/v1/records/{id}/state?at=...` | Карта на момент времени RFC 3339 |
| GET | `/api/v1/records/{id}/state?version=...` | Карта на выбранную версию |

Создание требует `{"staff_id":"UUID активного медработника"}`. Повторное создание возвращает 409 `RECORD_EXISTS`. Новая карта получает версию 1, пустые списки и событие создания с автором.

Пример сохранения (UUID заменяются реальными значениями):

```json
{
  "staff_id":"c0a2ca07-e031-4e04-ab04-5bd6c264a8c1",
  "expected_version":1,
  "commands":[
    {"type":"add_diagnosis","diagnosis_id":"12e575d0-0047-4be4-9e09-07f7e5aa8ffb"},
    {"type":"add_prescription","text":"Пить больше воды"}
  ]
}
```

От 1 до 100 команд за одно сохранение:

| type | Поля | Результат |
|---|---|---|
| `add_diagnosis` | `diagnosis_id` | Проверка справочника, добавление снимка с новым ID записи в карте |
| `remove_diagnosis` | `id` | Удаление записи диагноза из карты |
| `add_prescription` | `text` | Новое активное назначение с новым ID |
| `edit_prescription` | `id`, `text` | Удаление старого и добавление изменённого назначения с новым ID |
| `cancel_prescription` | `id` | Смена статуса на cancelled, назначение остаётся видимым |
| `remove_prescription` | `id` | Удаление назначения из текущего состояния с сохранением истории |

Для `remove_diagnosis` передаётся ID записи в ЭМК, а не `diagnosis_id` из справочника. Текст назначения — 3–128 символов. Отменённое назначение нельзя повторно отменить или редактировать. Повторный активный диагноз в одной карте запрещён. Все обязательные UUID должны быть ненулевыми.

Каждое успешное сохранение увеличивает версию ровно на 1. Несовпадение `expected_version` даёт 409 `VERSION_CONFLICT`; клиент сохраняет черновик и предлагает обновление. Ошибка любой команды откатывает весь запрос, включая ранее обработанные команды и события истории. Проверки справочников выполняются до транзакции. Их недоступность мешает новым изменениям, но не чтению карты и истории.

API не предоставляет отдельного метода разблокировки: это состояние UI. UI должен требовать выбора сотрудника перед редактированием, отправлять его ID при сохранении и возвращаться в просмотр после успеха.

## История и восстановление

Событие содержит `id`, `record_id`, `sequence`, `version`, `occurred_at`, `actor`, `type`, `entity_id`, `before`, `after`. Автор — снимок ID, имени, фамилии и должности. Данные диагноза — снимок ID справочника, кода и наименования. Переименование или удаление справочных записей не меняет старые события.

Редактирование назначения создаёт `prescription_removed` и `prescription_added` с одной версией и одним временем. Восстановление включает сохранение целиком и не показывает промежуточное состояние между этими событиями. Порядок задан sequence, время назначает БД в UTC, внутри карты оно строго возрастает между сохранениями.

Для восстановления передаётся ровно один параметр: `at` или `version`. Время с часовым смещением принимается и переводится в UTC; положительное смещение в URL следует кодировать как `%2B`. Момент до создания карты и несуществующая версия возвращают 404. Момент после последнего сохранения возвращает последнее состояние. Ответ имеет тот же формат, что текущая карта, с историческими `version`, `updated_at` и `state`.

История доступна только для чтения: методов изменения/удаления событий и удаления ЭМК нет.

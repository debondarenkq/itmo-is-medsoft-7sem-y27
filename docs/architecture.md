# Учебная HIS: проект архитектуры

Статус: согласованная архитектура; backend реализован, десктопный UI — следующий этап.

## Стек и границы сервисов

- Клиент: Dart + Flutter (выбор согласован), десктопное приложение под macOS и Windows с общей кодовой базой UI. Два раздела: администрация и рабочее место медработника. Без аутентификации. React и Vite не используются.
- Nginx: единая точка входа в backend и маршрутизация `/api/v1/staff`, `/api/v1/diagnoses`, `/api/v1/patients` и `/api/v1/records`. Десктопный клиент обращается к одному базовому адресу API.
- `staff-service`: Go, медработники, CRUD, мягкое удаление.
- `catalog-service`: Go, диагнозы, CRUD, импорт диагнозов из выбранного пользователем JSON-файла. Новый справочник пуст.
- `clinical-service`: Go, пациенты, ЭМК, диагнозы и назначения внутри ЭМК, история и восстановление состояния.
- HTTP/JSON, `net/http` + `gorilla/mux` (выбор согласован), PostgreSQL через `pgx`, SQL-миграции через `pressly/goose/v3` (выбор согласован), структурированные логи через `slog`.
- Docker Compose для запуска backend. Десктопный клиент собирается и запускается отдельно. Один экземпляр PostgreSQL, три отдельные базы и три отдельных пользователя. Каждый сервис владеет своей БД; доступ к чужим таблицам запрещён.
- OpenAPI описывает публичные API. Межсервисное взаимодействие — прямой HTTP/JSON с таймаутами; Nginx служит точкой входа для десктопного клиента.

Для Flutter согласованы встроенный Material 3 и встроенный `Navigator` для переходов между экранами; основные разделы переключаются боковым меню. Отдельный UI kit и `go_router` не нужны. Для состояния предлагается начать со встроенных средств Flutter (`ChangeNotifier`/`ListenableBuilder`), для HTTP/JSON — `package:http`; дополнительные библиотеки состояния пока не согласованы. Базовый адрес API задаётся через `--dart-define=API_BASE_URL=...`; клиент не подключается к БД напрямую. Сборки выпускаются отдельно: macOS на macOS, Windows на Windows, в дальнейшем возможно через соответствующие runners CI. Для локального показа backend запускается через Compose, затем отдельно запускается десктопный клиент.

Пациенты и ЭМК принадлежат одному сервису, потому что ограничения «одна ЭМК на пациента» и «нельзя удалить пациента с ЭМК» должны выполняться атомарно. Отдельные микросервисы для этих сущностей потребовали бы распределённой координации без пользы для лабораторной.

Каждый Go-сервис хранит свои SQL-миграции Goose в собственном каталоге `migrations/` и применяет их только к своей БД. Миграции имеют секции `-- +goose Up` и `-- +goose Down`; таблица версий Goose независима в каждой БД. Для локального запуска Compose сначала выполняет отдельную команду миграции соответствующего сервиса, затем запускает его HTTP API. Импорт диагнозов остаётся отдельной операцией API: пользователь выбирает файл, а backend валидирует и сохраняет его содержимое. Миграции и запуск сервиса не добавляют диагнозов.

## Данные

Все сущности получают UUID. Временные отметки — `timestamptz`, хранятся и передаются в UTC; API возвращает RFC 3339. Сервер назначает время событий; даты рождения — `date`.

### Медработники

`staff(id, first_name, last_name, position, created_at, updated_at, deleted_at)`.

Имя, фамилия и должность — 3–24 символа после удаления пробелов по краям. Удаление устанавливает `deleted_at`, запись сохраняется. Удалённый сотрудник не может быть автором новых изменений ЭМК.

### Справочник диагнозов

`diagnoses(id, code, name, created_at, updated_at, deleted_at)`.

Код — ровно 6 символов, уникален; наименование — 3–24 символа, уникально. Предлагается мягкое удаление: диагноз исчезает из списка доступных для назначения, но сохраняется для ранее созданных карт. Уникальность распространяется и на удалённые записи. Принудительная загрузка принимает содержимое выбранного JSON-файла (1–1000 диагнозов, до 1 MiB). Бизнес-модуль проверяет все поля и отсутствие повторяющихся кодов/наименований в файле, затем передаёт список репозиторию. Импорт выполняет upsert по коду: обновляет название и восстанавливает активность существующих записей, создаёт отсутствующие; прочие записи не меняются. Повторный импорт не создаёт дубликатов, конфликты наименований в БД откатывают весь импорт. В исходном коде сервиса нет встроенного справочника; пять примеров находятся в отдельном файле `examples/diagnoses.json` для ручного выбора.

### Пациенты и ЭМК

`patients(id, first_name, last_name, middle_name, birth_date, administrative_sex, comment, created_at, updated_at)`.

Имя и фамилия — 1–64 символа, отчество — необязательное, при наличии 1–64. Дата рождения обязательна, не в будущем. Пол: `M`, `F`, `UNKNOWN`, в UI: М, Ж, НУ. Комментарий — до 32 символов.

`records(id, patient_id UNIQUE REFERENCES patients(id) ON DELETE RESTRICT, version, state JSONB, created_at, updated_at)`.

ЭМК не удаляется. Внешний ключ запрещает физическое удаление пациента с картой, а уникальность `patient_id` обеспечивает не более одной карты, включая конкурентные запросы. Создание карты при конфликте возвращает 409. События истории также ссылаются на ЭМК через внешний ключ внутри БД клинического сервиса; между базами разных сервисов внешних ключей нет.

Текущее содержимое ЭМК хранится в `records.state` как JSONB с двумя типизированными списками. Это материализованное состояние, которое записывается атомарно вместе с событиями. Отдельные таблицы для списков на этом этапе не нужны: вся карта редактируется как единый агрегат, а история остаётся в отдельной таблице с индексами по времени и версии. API валидирует структуру и данные списков.

Состав состояния и истории:

- `state.diagnoses`: идентификатор записи, ЭМК, внешний UUID диагноза, снимок кода и наименования. Повторное добавление уже присутствующего диагноза возвращает 409.
- `state.prescriptions`: идентификатор, ЭМК, текст 3–128 символов, статус `active`/`cancelled`. При редактировании старое назначение удаляется из текущего состояния и создаётся новое с новым ID.
- `record_events`: ЭМК, порядковый номер события, версия сохранения, серверное время, автор (UUID и снимок имени/фамилии/должности), тип действия, полные данные до и после действия в JSONB. Уникальная пара `(record_id, sequence)` задаёт порядок событий.

Снимки медработника и диагноза сохраняют контекст истории при последующем редактировании справочников. История добавляется только через клинический сервис, изменение или удаление событий не предусмотрено API.

## Сохранение ЭМК и восстановление истории

1. Карта открывается только для просмотра. Пользователь нажимает «Редактировать» и обязательно выбирает активного медработника. Это блокировка только в UI.
2. Изменения накапливаются в черновике. Отмена редактирования отбрасывает черновик.
3. Сохранение отправляет `staff_id`, `expected_version` и набор команд одним запросом.
4. Клинический сервис проверяет медработника через staff-service и новые диагнозы через catalog-service; сохраняет полученные снимки. Проверки выполняются по HTTP/JSON до открытия транзакции БД. При недоступности нужного сервиса возвращает 503, ничего не записывает. Чтение пациентов, текущей карты и истории продолжает работать без этих межсервисных проверок.
5. В одной транзакции блокируется строка ЭМК, проверяется версия, применяются команды, записываются события и увеличивается версия. Любая ошибка откатывает всё сохранение.
6. После успеха UI снова блокирует редактирование. При конфликте версии (409) сохраняет черновик и предлагает обновить карту.

Без `staff_id` изменения всегда отклоняются API. Межсервисная проверка подтверждает активность сотрудника/диагноза на момент проверки; атомарность с последующим удалением в другом сервисе не обещается. Для учебной системы это допустимо; локальное сохранение ЭМК остаётся атомарным.

Создание карты тоже требует автора и создаёт первое событие. Типы событий: создание карты, добавление/удаление диагноза, добавление/отмена/удаление назначения. Отмена сохраняет назначение со статусом `cancelled`. Редактирование назначения записывает два события: удаление старого и добавление нового в одной транзакции, одной версии и с одним временем сохранения.

Состояние на момент `at` восстанавливается применением всех событий сохранений с `occurred_at <= at` по порядковому номеру. События одной версии применяются целиком: промежуточное состояние между удалением и добавлением при редактировании назначения не показывается. При сохранении сервер назначает строго возрастающее время между версиями внутри карты. Дополнительно доступен запрос состояния по версии для однозначного выбора сохранения при одинаковых временных отметках.

## Основные API

- `/api/v1/staff`: список, создание; `/{id}`: получение, изменение, мягкое удаление.
- `/api/v1/diagnoses`: список, создание; `/{id}`: получение, изменение, мягкое удаление; `/import`: импорт выбранного файла справочника.
- `/api/v1/patients`: список, создание; `/{id}`: получение, изменение, физическое удаление с проверкой ограничения БД.
- `/api/v1/patients/{id}/record`: создание и получение единственной ЭМК.
- `/api/v1/records/{id}/changes`: атомарное применение команд с обязательным автором и ожидаемой версией.
- `/api/v1/records/{id}/history`: события с авторами и данными изменений.
- `/api/v1/records/{id}/state?at=...` либо `?version=...`: восстановленное состояние.

Общий формат ошибок: код и понятное сообщение, для ошибок валидации — конкретные поля. 400 — некорректный запрос, 404 — отсутствие сущности, 409 — конфликт/нарушение бизнес-ограничения, 503 — недоступность зависимого сервиса, 500 — внутренняя ошибка. JSON-запросы и ответы имеют `Content-Type: application/json`. Списки поддерживают поиск и пагинацию.

## Проверки

Unit-тесты проверяют бизнес-логику и валидацию с дублями репозиториев и HTTP-клиентов. Интеграционные тесты с изолированным PostgreSQL покрывают запрет удаления пациента с картой, уникальность карты, конкурентное создание карты и удаление пациента, обязательность автора, атомарность сохранения, конфликт версий, мягкое удаление медработника, повторную загрузку справочника и восстановление карты до/после каждого вида изменения. Отдельно проверяется пара событий при редактировании назначения и неизменность исторических снимков после изменения справочников.

Сквозной сценарий UI: загрузить справочник, создать сотрудника и пациента, создать карту, разблокировать её выбором сотрудника, добавить диагноз и назначение, сохранить, изменить и отменить назначение, проверить историю и восстановление на выбранный момент, получить отказ удаления пациента с ЭМК.

## Этапы и коммиты

1. Согласованный план архитектуры, README и инструкция запуска.
2. Каркас Go-сервисов, Compose, Nginx, миграции, health endpoints.
3. Медработники и справочник диагнозов с валидацией и загрузкой.
4. Пациенты и создание ЭМК с ограничениями БД.
5. Атомарное редактирование, история, восстановление и интеграционные тесты.

Пользователь разрешил создавать коммиты и выполнять push от его имени для этой лабораторной. Используется существующий автор Git, без изменения глобальных настроек. Коммиты делаются по завершённым этапам после подходящих проверок; push — в согласованную рабочую ветку без force push.

## Самостоятельность сервисов

Весь проект находится в одном каталоге: `services/staff`, `services/catalog`, `services/clinical` и `desktop`. Каждый Go-сервис имеет собственные `go.mod`, `go.sum`, Dockerfile, модели, HTTP-утилиты и миграции. Общего Go-модуля, `go.work`, общих Go-пакетов и локальных зависимостей через `replace` нет. Каталог любого сервиса можно перенести и собрать отдельно; во время работы связи с другими сервисами задаются HTTP-адресами из конфигурации.

## План экранов

Для Flutter-клиента приняты шесть основных экранов: список и карточка медработника, справочник диагнозов, список и карточка пациента, ЭМК с вкладками диагнозов/назначений/истории. Подробности — в `docs/gui.md`.
